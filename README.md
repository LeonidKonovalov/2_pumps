# Управление насосами P1/P2

Контроллер на IEC 61131-3 Structured Text для двух насосов, работающих по схеме
основной/резервный (duty/standby) с управлением по уровню и автоматическим
переключением на резерв при отказе.

- **Среда разработки:** OpenPLC Editor (компилятор STruC++)
- **Целевая платформа (отладка):** OpenPLC Simulator
- **Язык:** Structured Text, IEC 61131-3

---

## 1. Назначение

Контроллер управляет насосами P1 и P2 по уровню в резервуаре, гистерезис **30%–80%**.
Первый насос основной, второй резервный.

В `AutoMode` выполняется автоматический запуск, перезапуск и переключение на резерв.
`EmergencyInput` — аварийная остановка, наивысший приоритет (прерывает любое состояние).

---

## 2. Состояния

| Состояние | Назначение |
|---|---|
| `IDLE` | Насосы остановлены |
| `STARTING` | Запуск выбранного насоса |
| `RUNNING` | Насос работает |
| `STOPPING` | Остановка насоса |
| `SWITCHING` | Переключение на резерв |
| `FAULT` | Аварийное состояние |
| `EMERGENCY` | Аварийная остановка |

Сопутствующие перечисления:

- `ActivePump`: `NONE` / `P1` / `P2`
- `StopReason`: `NORMAL_STOP` / `PUMP_FAULT` / `EMERGENCY_STOP`

> **Важно:** для всех трёх перечисляемых типов необходимо явно задать `Initial Value`
> (`IDLE`, `NONE`, `NORMAL_STOP`). Если поле оставить пустым, компилятор берёт первый
> литерал по порядку объявления типа — контроллер может стартовать в непредсказуемом
> состоянии.

---

## 3. Основная логика (нормальный цикл)

```
Level < 30% + AutoMode
   ↓
IDLE
   ↓
STARTING
   ↓ P*_Run
RUNNING
   ↓ Level > 80%
STOPPING
   ↓ P*_Run = FALSE
IDLE
```

---

## 4. Отказ насоса

```
RUNNING
   ↓ P*_Fault
STOPPING
   ↓ P*_Run = FALSE
SWITCHING
   ↓
STARTING (резервного)
   ↓ P*_Run
RUNNING
```

Если резервный насос недоступен → `FAULT` + `Alarm`.
В `ManualMode` (`AutoMode = FALSE`) автоматического переключения нет.

---

## 5. Таймеры

### `StartTimer` = 5 с
Если `P*_Run` не появился за 5 секунд после команды пуска:

| Режим | Переход |
|---|---|
| `AutoMode` | `STARTING` → `STOPPING` → `SWITCHING` |
| `ManualMode` | `STARTING` → `FAULT` |

### `StopTimer` = 5 с
Если насос не подтвердил остановку: `STOPPING` → `FAULT`

---

## 6. Аварии и диагностика

| Сигнал | Условие |
|---|---|
| `Warning` | `P1_Fault OR P2_Fault` |
| `Alarm` | `P1_Fault AND P2_Fault` |

### Emergency

```
EmergencyInput = TRUE
   ↓
EMERGENCY
   ↓
P1_Start = FALSE, P2_Start = FALSE
```

После снятия `EmergencyInput` и подтверждения остановки обоих насосов → `IDLE`.

---

## 7. Сброс FAULT

Выход из `FAULT` разрешён **только** при одновременном выполнении всех условий:

```
ResetCommand = TRUE
P1_Run       = FALSE
P2_Run       = FALSE
P1_Fault     = FALSE
P2_Fault     = FALSE
```

После сброса: `FAULT` → `IDLE`, `StopReason` → `NORMAL_STOP`.

---

## 8. Основные сигналы

| Сигнал | Направление | Тип | Назначение |
|---|---|---|---|
| `Level` | DI/AI | `REAL` | Уровень в резервуаре, % |
| `P1_Run` | DI | `BOOL` | Работа P1 (обратная связь) |
| `P1_Fault` | DI | `BOOL` | Неисправность P1 |
| `P2_Run` | DI | `BOOL` | Работа P2 (обратная связь) |
| `P2_Fault` | DI | `BOOL` | Неисправность P2 |
| `EmergencyInput` | DI | `BOOL` | Аварийная остановка |
| `AutoMode` | DI | `BOOL` | Разрешение автоматического режима |
| `ResetCommand` | DI | `BOOL` | Команда сброса аварии |
| `P1_Start` | DO | `BOOL` | Запуск P1 |
| `P2_Start` | DO | `BOOL` | Запуск P2 |
| `Warning` | DO | `BOOL` | Предупреждение |
| `Alarm` | DO | `BOOL` | Авария |

---

## 9. Порядок выполнения в скане

Тело `FB_PumpController` выполняется строго последовательно:

1. **DEFAULT OUTPUTS** — сброс `P1_Start`, `P2_Start`, `Warning`, `Alarm` в `FALSE`
2. **TIMERS** — обновление `StartTimer` и `StopTimer`
3. **EMERGENCY** — проверка высшего приоритета
4. **DIAGNOSTICS** — расчёт `Warning` / `Alarm`
5. **STATE MACHINE** — `CASE ControllerState` (читает состояние на начало скана)
6. **OUTPUT COMMANDS** — `CASE ControllerState` (использует уже обновлённое состояние)

Выходы формируются **после** стейт-машины. Благодаря этому, если внутри одного скана
произошёл переход `STARTING → STOPPING`, команда пуска `P1_Start` уже не включится.

## 10. Структура проекта

```
pump/
├── Function Blocks/
│   └── FB_PumpController      # вся логика управления
├── Programs/
│   └── main                   # вызов экземпляра Pump : FB_PumpController
└── Data Types/
    ├── E_ControllerState
    ├── E_ActivePump
    └── E_StopReason
```

`main` не содержит логики — только вызов блока и проброс сигналов:

```st
Pump(
    AutoMode       := AutoMode,
    Level          := Level,
    EmergencyInput := EmergencyInput,
    P1_Run         := P1_Run,
    P1_Fault       := P1_Fault,
    P2_Run         := P2_Run,
    P2_Fault       := P2_Fault,
    ResetCommand   := ResetCommand
);

P1_Start := Pump.P1_Start;
P2_Start := Pump.P2_Start;
Warning  := Pump.Warning;
Alarm    := Pump.Alarm;
```

## 11. Верификация

Логика портирована на Python и прогнана через pytest — 10 сценариев (T01–T10),
все пройдены.

```bash
pytest test_pump_controller.py -v          # все тесты
pytest test_pump_controller.py -s -k T05   # с пошаговым выводом по сканам
```

| № | Из состояния | Событие | Ожидается |
|---|---|---|---|
| T01 | `IDLE` | `Level=20%`, `AutoMode=1` | `STARTING` P1, `P1_Start=1` |
| T02 | `STARTING` P1 | `P1_Run=1` | `RUNNING` P1 |
| T03 | `RUNNING` P1 | `Level=85%` | `STOPPING`, оба `Start=0` |
| T04 | `STOPPING` P1 | `P1_Run=0` | `IDLE` |
| T05 | `STARTING` P1 | 5 с без `Run` | `STOPPING` → `SWITCHING` |
| T06 | `STOPPING` P1 | `P1_Run=0` + `Fault` | `SWITCHING` |
| T07 | `SWITCHING` P1 | P2 исправен | `STARTING` P2, `P2_Start=1` |
| T08 | `STARTING` P2 | `P2_Run=1` | `RUNNING` P2 |
| T09 | `RUNNING` P2 | `P2_Fault=1` | `STOPPING` |
| T10 | `STOPPING` P2 | `P2_Run=0` | `SWITCHING` |

### Особенность T05

Если насос ни разу не подтвердил запуск (`P*_Run` всё время `FALSE`), то после
таймаута `StartTimer` контроллер входит в `STOPPING`, но условие выхода
(`NOT P*_Run`) выполняется мгновенно — переход в `SWITCHING` происходит уже на
следующем скане. Состояние `STOPPING` проходится «транзитом».

На физическое поведение это не влияет: в обоих состояниях `P1_Start`/`P2_Start`
удерживаются в `FALSE`. Эффект значим только для SCADA с низкой частотой опроса —
кратковременное `STOPPING` может быть не зафиксировано. Если промежуточное состояние
нужно в журнале событий, использовать событийную запись по фронту (`R_TRIG`), а не
периодический опрос.

## 12. Расхождение спецификации и реализации

В разделе 5 исходной спецификации указан переход по таймауту запуска:

```
STARTING → SWITCHING   (AutoMode)
```

В реализации переход выполняется **через промежуточное состояние**:

```
STARTING → STOPPING → SWITCHING   (AutoMode)
```

Причина: перед переключением на резерв необходимо убедиться, что предыдущий насос
фактически остановлен (`NOT P*_Run`), иначе возможен одновременный пуск обоих насосов.
Состояние `STOPPING` выполняет эту проверку и одновременно взводит `StopTimer` на
случай, если насос «завис» во включённом состоянии.

Конечный результат совпадает со спецификацией, отличается только путь. Требует
согласования с заказчиком: либо обновить спецификацию, либо явно задокументировать
промежуточное состояние.

## 13. Ограничения среды (STruC++ / OpenPLC)

Выявлены при отладке, отличают STruC++ 0.6.2 от промышленных CODESYS-совместимых сред:

- **Идентификаторы регистронезависимы.** Вход `Emergency` конфликтовал с литералом
  перечисления `EMERGENCY` — потребовалось переименование в `EmergencyInput`.
- **Литералы перечислений должны быть уникальны в рамках всего проекта.** Одинаковое
  имя `EMERGENCY` в `E_ControllerState` и `E_StopReason` вызывало ошибку на этапе
  генерации C++ — второй литерал переименован в `EMERGENCY_STOP`.
- **Множественные метки `CASE` через запятую не поддерживаются.** Конструкция
  `STARTING, RUNNING:` требует разбиения на отдельные блоки с дублированием тела.
- **`FUNCTION_BLOCK` / `END_FUNCTION_BLOCK` добавляются средой автоматически** —
  вручную в тело POU их вставлять не нужно.
- **Переменные объявляются в табличном редакторе**, а не через `VAR ... END_VAR`
  в тексте.

Эти ограничения не противоречат IEC 61131-3 — они следствие того, что STruC++ является
облегчённой реализацией для трансляции ST в C++. В CODESYS-совместимых средах
(REGUL, ОВЕН) перечисленные конструкции поддерживаются штатно.
